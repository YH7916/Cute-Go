# 围棋教学 Prompt 评测方案

状态：**已完成一轮本地 DeepSeek 小样本实测，八场景矩阵尚未全部运行**。日期：2026-10-25；原始结果与限制见[真实模型基线](verification/2026-10-25-coach-real-model.md)。

本文规定可复跑的输入来源、评判标准与记录方式，不代表新版 prompt 已改善教学质量。`tests/coach-pi-runtime.test.mjs` 的真实 Pi SDK + 固定 SSE 回包验证程序链路、工具协议和输出校验；模型答案由 fixture 预先指定，不能用它证明模型理解了 prompt。检查 prompt 是否含某些关键词同样不能证明教学效果。

本轮不扩展工具、搜索、规则或响应格式。实际输出仍受 `domains/coach/response.ts` 约束：新 explain 正文统一 50 字以内、最多一句和三个引用，不设字数下限，能短则短；建议最多三个点，但合法点更多时完整绑定，不因超出建议丢弃云文案。旧 parts 材料不作为新模型输出协议。后台模型输出与前端实际展示应分别记录，不能把本地兜底当成云端答对。

## 需要检验的决策策略

1. **先识别问题。** 具体问题先直接回答，再解释必要原因；不机械追加下一步。`hint` 和默认讲解才使用危险优先策略。明确问上一手或一般概念时，不用别处的危险抢走主题。
2. **选择足够的依据。** 可以组合当前事实与一般规则解释因果，不要求照抄 variants；不能新增未验证的棋块计数、坐标、变化、死活或最优结论。课程概念不能证明棋盘上某块棋已具备相应条件。
3. **按需读工具。** 首轮已收到完整当前快照，优先直接回答；`read_position` 和 `read_engine_analysis` 用于可选复查，`read_teaching_choices` 只筛选已有条目；不应为重复已有信息追加工具轮次。工具缺失证据时不声称重新搜索过。
4. **区分当前与过去。** conversation 用于理解指代；current/earlier 都不是新的棋盘证据，earlier 更不能覆盖当前局面。换局、悔棋和落子后，以本次事实为准。
5. **保留有用的部分。** 证据不足时先说明相关已知和具体未知。仅在无相关可引用材料时使用 `unavailable`，不要把有限证据一律变成固定拒绝。
6. **按场景决定是否说话。** 手动请求必须回应；自动场景可在没有值得打断玩家的提醒时静默。自动请求通常没有 conversation，不能要求模型凭空判断是否比上次新增了信息。

## 输入必须来自实际代码或实际对局

评测中的坐标、气数、提子数和示例变化都由运行结果确定。下文的“目标棋块”“候选甲”等是选择条件，不是已经构建、已经验证的固定棋形；不要把描述中的预期数量手工写进 evidence。

推荐两种来源：

- **产品路径：** 在 H5 正常对局或导入合法 SGF，再通过现有状态入口落子、停着、悔棋、试下。记录棋谱、当前游标、执子、行棋方、贴目与问题。在浏览器网络面板保存本次 `/api/coach` 的 JSON 请求体和响应体；不要导出 Authorization、API key 或带凭据的完整 HAR。
- **源码路径：** 从 `createInitialPosition` 开始，每步先调用 `core/go/rules.ts` 的 `attemptMove` 验证合法性，再调用 `recordMove`，停着和悔棋使用 `recordPass`、`undoPosition`。通过 `buildCoachEvidence`、`buildCoachTeachingChoices`、`buildCompactCoachContext` 生成材料，或直接运行 `executeCoachAgent` 使用完整生产路径。需要测试内装载源码时继续使用 `tests/helpers/loadTestModule.mjs`，不复制装载器。

可参考现存回归中的构造方式，但先区分材料性质：

| 参考入口 | 可复用内容 | 不可据此声称 |
| --- | --- | --- |
| `tests/coach-evidence.test.ts` 的 `play`、`threatened` 与提子/连接用例 | 用真实规则计算棋块、气和一步变化；最后一手经合法落子重放 | 摆放初始棋子就是完整真实棋谱，或这些局面已通过 ONNX 实测 |
| `tests/coach-context-budget.test.ts` 的指定安静棋块/气点用例 | 棋块锚点不等于问题坐标时的上下文选择 | 压力测试里手造的长历史是合法对局；应避免拿这种压力材料做教学质量评测 |
| `tests/coach-question-analysis.test.mjs` | 提问坐标如何进入分析请求 | 其 mock 分析是实际搜索结果 |
| `tests/coach-engine-ranking.test.ts`、`tests/coach-synthesis.test.ts` | 协议及引用测试的形状 | 手写 visits、prior、胜率或变化是模型推理证据 |
| `scripts/verify-onnx-browser.mjs`、H5 局中手动讲解 | 真正加载模型及采集局中分析的入口 | 单次输出证明最佳手、死活或教学质量提升 |

引擎场景必须保留实际生成的 `engineAnalysis`，并确认位置、行棋方、贴目对应。`source: local-katago` 字符串本身不是实测证明。没有真实引擎材料时把该场景标为“未覆盖”，不能用填入的数值补齐。初始摆棋若无法通过 Worker 的历史重放一致性检查，应使用真实对局重建；不能绕开检查伪造引擎输入。

反事实配对也应通过实际状态变化生成：落一手、悔一手、切换合法局面或改变提问后重新计算。不能只改 evidence 的气数而保留不匹配的棋盘。仅用于验证提示边界的合成会话、缺失引擎对照须明确标注为构造输入，不能称为真实用户历史或引擎故障实测。

## 八个评测场景

每个场景至少准备一组反事实配对。用例建立后固定棋谱/完整状态、问题和请求体，比较不同 prompt 时复用同一份材料；不得为了让答案通过而补写 choices。

| ID | 构建与提问 | 期待行为 | 判失败的表现 | 配对操作 |
| --- | --- | --- | --- | --- |
| P01 具体数气 | 从合法局面选一个安静棋块，问题使用该块实际坐标问“有几口气”；保留同时存在的通用局面建议 | 先回答目标棋块当前气数，必要时解释整块共用气；引用实际 group，数字对应生产计算 | 只讲开局或下一步；答其他棋块；拿 libertyExamples 长度当完整气数 | 合法落子改变该块气数后重算；或改问同局另一棋块，答案应随对象变化 |
| P02 一般规则 | 问“落下之后没气就一定不能下吗”，使用实际选出的 suicide/capture 规则材料 | 解释先提走对方无气棋块，再检查自身整块棋的气；无须引擎也能回答概念 | 把“看似无气”直接说成非法；遗漏先提子的例外；机械 unavailable；编当前盘面结论 | 同一问题分别使用存在/不存在一步提子机会的合法局面；规则条件保持一致，当前结论只能有据而说 |
| P03 hint 的优先级 | 选择己方处于打吃、且存在真实规则验证解围候选的局面；问“我应该先观察什么”；若有真实远处引擎候选一并保留 | 指出当前危险及可以比较的接长/提子条件，保留反提等限制；指导观察或试下，不代替玩家落子 | 无视打吃只推荐远处引擎点；把候选称为必须、保证安全或最佳；把对手的棋误称己方 | 用真实解围或提子后局面重算，旧危险消失就不继续提醒；黑白互换用独立验证局面 |
| P04 上一手与全局得失 | 重放一次合法连接、提子或停着，分别问“这手改变了什么”和“这手亏了多少” | 解释已验证的当前变化；缺乏全局衡量依据时明确范围，不发明精确差距 | 编造胜率变化或精确得失；冒称云端比较过其他着手；把全局手数当该颜色落子次数 | 保留当前位置，改为问一般概念；或悔棋后重放另一手，上一手依据必须重新生成 |
| P05 引擎示例而非强制变化 | 采集实际局中 ONNX 候选及示例，问题用其中实际坐标问“这个候选后面怎样理解” | 使用首轮已有 engine，必要时复查；只描述记录中的示例顺序，称为可在试下观察的变化；不把首步气数沿用到后续点 | 未获记录却编对手应法；把示例当强制；输出访问数/胜率或精确比分；把未访问候选说成已深算 | 同局构造明确标记的“移除引擎字段”对照，保留真正的规则材料；仍可解释规则，但不能继续引用已移除的 engine 项 |
| P06 跨局面追问 | 先在局面甲真实提问并保留回答；合法落子或悔棋到局面乙后，问“刚才那块现在呢”，确保工具材料能定位该对象 | 用 conversation 理解所指，答案依据乙的 group/候选；旧回答不能代替现有事实 | 沿用甲的气数或危险；把 earlier 当当前；对象不明时擅自选一块棋 | 对同一对象分别采集 current 历史和 earlier 历史；如构造会话只改归属标签，明确记为合成边界测试 |
| P07 证据不足仍能解释 | 问当前目标棋块“气多了是不是就活了”，提供实际 group、相关气/试下概念，没有完整死活证明 | 先解释当前可确认事实，再说明尚不能据此判断后续安全；给与该未知相关的观察方式 | 断言已活；把课程两眼概念当当前棋块已有两眼；有可用概念却只输出固定 unavailable | 同一局面改问“气是什么/为什么连着共用气”，应直接讲概念；改问不可证实的全局胜负时保留边界 |
| P08 自动与手动 | 对相同已生成证据分别使用自动场景和具体手动提问；记录自动请求是否先被端侧门控拦截 | 手动必须有回应；自动无值得打断的提醒时可静默，不能制造危险；不声称知道未提供的上次提醒 | 手动 SILENT；仅因“自动”就无条件沉默；凭空判断与上次重复；把未发送请求记为模型静默 | 只改变 proactive 的对照须标为构造请求；产品自然自动触发另记录“端侧未发送/云端静默/云端回答”，不能混记 |

P05 的示例可能长于正文能容纳的坐标数量。优先选择与问题有关的三个关键点，或概括需要观察的关系；完整性与棋理正确性需人工核验，renderer不以引用项字面坐标列表代替语义判断。候选先后及是否实际访问以真实数据为准，不把数组首项自动解释成最优。

## 真模型运行方法

先完成程序级检查，再进行质量评测；程序级通过不填写为表格中的模型通过。

```powershell
npm test -- tests/coach-pi-runtime.test.mjs tests/coach-pi-http.test.mjs tests/coach-response-validation.test.ts tests/coach-context-budget.test.ts
npm run build
# 与前端实际启动的 origin 一致；更换端口后也要更新此值。
$env:COACH_ALLOWED_ORIGIN = 'http://localhost:3001'
npm run coach:start
```

另一个终端执行 `npm run dev`，按控制台给出的地址打开 H5。使用当前陪练设置填写后台地址、已支持的供应商、模型及自己的 API key；模型选择与 BYOK 运行细节以 `shared/coach.ts`、设置页面和 [Pi 后台说明](pi-coach-backend.md) 的当前实现为准，不把供应商密钥写入本评测记录。

逐例操作：

1. 从固定棋谱/完整状态恢复到指定游标，确认棋盘尺寸、执子、行棋方和贴目。局中引擎场景等待真实模型可用；复盘领地图分析不能视为已经传给讲解的 engineAnalysis。
2. 使用指定问题发起一次真实请求。保存本次请求体和响应体，保留 source/fallback 情况；如没有请求，记录端侧门控或配置状态，不补造模型结果。
3. 用生成上下文时的同一份 `choices` 调用 `renderCoachResponse(reply.text, choices, proactive, boardSize, maxParts)`。浏览器正常路径由 `executeCoachAgent` 已完成此检查；程序重放需要保留 builder 返回的 choices，不能临时新增引用。记录通过、拒绝或 unavailable/silent。
4. 人工对照请求中的事实评判“是否回答所问、因果是否有据、条件是否保留”。`source: cloud` 或 renderer 通过只证明被接受，不等于语义正确；`source: local` 要区分没有请求、服务失败和无效正文兜底。
5. 运行对应反事实输入，比较答案有没有跟随事实、对象或场景变化。建议每个输入分别运行三次并保存每次结果；不只挑最好的一次。重放相同快照时保持采集到的 evidence 不变，避免同时改变搜索采样与 prompt。
6. 比较两个 prompt 时记录模型 ID、供应商、prompt 内容及文件哈希、请求体哈希、运行时间和实际错误。同一模型 ID 也可能由供应商更新；只描述本次样本，不外推全部模型。

当前 HTTP 成功响应只有 `{text}`，不返回工具事件或 token 使用量。首轮 `read_position` 由 runtime 强制，但最终文字不能证明可选 `read_engine_analysis` 是否被调用。工具路由若需逐例人工核验，可在本地调试器观察 `server/coach/runtime.ts` 已有 `agent.subscribe` 的 `tool_execution_start/end` 事件；只记录工具名、顺序和成功/失败，不记录密钥。没有观察到事件的运行把“工具路径”记为“未观测”，不能凭答案提到引擎就判通过，也不要求为本方案给生产 HTTP 增加调试字段。

## 判分与结果记录

每次独立记录以下项，不使用“prompt 包含关键词”代替评判：

| 维度 | 通过条件 |
| --- | --- |
| 问题命中 | 回答实际所问对象与问题；补充建议不抢主题 |
| 依据与推理 | 引用支持对应陈述；因果解释没有增加未经验证的条件或结果 |
| 限制与不确定性 | 区分规则、浅搜、概念和旧历史；必要前提、例外、未知均保留 |
| 教学价值 | 新手能理解原因或知道该观察什么，不是无关口号或机械拒绝 |
| 输出契约 | JSON、有效引用ID、棋盘范围与标记绑定、字数与句数经真实 renderer 接受；事实与数量单独按规则判定 |
| 工具与运行 | 实际观察到时记录读取顺序、额外调用、取消；未观察就明确留空 |

编造坐标/数量、错用旧局面、无依据断言死活/最佳、泄露凭据、手动静默属于必须修复的问题，不能被语言流畅抵消。规则正确但未回答问题、过度拒绝或重复泛泛建议也记录失败，不通过改提示后的单次好答案抹去。

| --- | --- | --- | --- | --- | --- | --- |
| 9路数气、标记与追问子集 | 见真实模型基线的输入与哈希 | DeepSeek deepseek-flash，见基线prompt哈希 | 14次完整捕获 | 6条云文案展示、8条本地回退 | 原文13/14事实正确；不是通用准确率 | 每条usage为1次模型调用；未记录工具事件 |

## 当前能力和约束，避免误判

- 局中讲解复用端侧规则与唯一 ONNX Worker；规则可验证当前棋块和一步变化，不是完整死活求解。真实对弈应手优先，模型忙碌、超时或证据过期时允许降级。
- 文本提问入口 `coachQuestionPoints` 当前最多提取两个点，因此该路径常见预算为 8/16/24 次访问；底层分析接口最多接受三个点、上限 32 次，二者不能混称。
- 示例变化最多四手；记录只证明这些着手经过合法性检查，不证明对手只有该应法。估计统一黑方视角，软领地估计不是官方精确分差、终局计分或胜负保证。
- 复盘开启领地图有独立 ONNX 分析，但 `AppController` 只在未终局的 playing 模式向 coach 提供局中分析回调。复盘或终局云讲解没有该回调，不应期待自动获得对应 engineAnalysis。
- `read_position` 返回完整棋盘与本次选出的教学项，`read_teaching_choices` 不能取回预算外的课程；引擎工具不新增搜索。conversation 仅在具体问题时按预算提供，最多最近三轮。
- renderer不再对数量、坐标或确定性词做引用项字面匹配；真实模型负责依据本轮事实组织文案，评测必须另行核对数量、因果和不确定性，不能把格式通过当成棋理正确。
- `questionReferences`由本地已显示标记解析，供当前选材和模型定位；旧点的当前棋子、气数与提子结果必须重新读取本轮棋盘，不得复用旧结论。
- `unavailable` 会变成固定本地文案；记录时保留原始模型协议，不能把固定文案当模型生成的具体解释。

本方案完成只表示评测范围和执行方法可供评审；完成真实模型运行、保留证据并逐项判定后，才能填写具体质量结论。
